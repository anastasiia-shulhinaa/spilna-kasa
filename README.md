# Спільна каса 💗

Вебзастосунок для спільного обліку фінансів у групах: учасники вносять витрати, система рівно ділить їх до копійки, рахує баланси й показує, хто кому скільки винен.
Поділ порівну, точними сумами або за чеком із фото, експорт в Excel. Демо поточної версії для етапу 4 (модуль 2, команда МІ-41).

**Стек:** Python 3.12+ · FastAPI · SQLAlchemy 2 · SQLite · Pillow · openpyxl · pytest — TypeScript · React 18 · Vite · Tailwind CSS · TanStack Query.

## Запуск (Windows)

Потрібні Python 3.12+ і Node.js 20+.

```powershell
cd spilna-kasa
.\dev.ps1          # перший запуск сам встановить залежності й створить демо-дані
.\dev.ps1 -Reset   # повернути демо-дані до початкового стану перед показом
```

- Застосунок: http://localhost:5173
- API-документація (Swagger): http://localhost:8000/docs

> Якщо після оновлення коду сервер пише «Схема бази даних застаріла», запустіть `.\dev.ps1 -Reset`: база створиться заново з демо-даними.

## Сценарій демо (~5 хв)

**Основний сценарій (порівну)**
1. Увійти як **Іванна** → «Квартира» → показати код запрошення.
2. «+» → «Порівну» → 600 ₴, «Продукти», платила Іванна, ділимо на всіх → живий підсумок «По 200,00 ₴ кожному».
3. Вкладка «Баланси»: Іванна +400, Софія −200, Марина −200; список «хто кому винен».
4. В іншому вікні (інкогніто) увійти як **Софія** → «Повернути» 200 ₴ → її баланс 0, витрати групи лишаються 600 ₴. Вікно Іванни оновиться саме за кілька секунд.
5. Додати витрату 100 ₴ на трьох → частки 33,34 / 33,33 / 33,33 — жодна копійка не губиться.

**Точні суми (хто скільки з'їв)**
6. Увійти як **Марина** → «Карпати 2026» → «+» → «Точні суми» → 1500 ₴, «Ресторан». Іванна 600, Анастасія 300 → підказка «Залишилось розподілити 600,00 ₴» → «Решту — платнику» → «Розподілено все ✓» → додати.

**Чек із фото (кожна позначає своє)**
7. Увійти як **Анастасія** → «Карпати 2026» → банер «Колиба «Смерековий дим» — позначте, що ви замовляли».
8. На сторінці чека видно фото, позиції й аватарки тих, хто вже позначив. Торкнутися «Вареники», «Чай» і «Сирна тарілка» (спільна на трьох, ÷ 3) → унизу з'являється **«Зберегти мій вибір · 300,00 ₴»** → зберегти. Підсумки оновлюються для всіх.
9. Увійти як **Марина** (платила). Блок «Хто оплатив весь чек» дозволяє змінити платника. Кнопки фото: на телефоні **«Сфотографувати»** (камера) і **«З галереї»**, на комп'ютері — «Обрати файл». «Закрити чек і записати витрату» → торкнутися операції в стрічці: Іванна 600, Анастасія 300, Марина 600.
10. Новий чек: «+» → «За чеком» → обрати фото (можна взяти `backend/app/demo_assets/receipt_demo.png`), ввести позиції → «Створити чек». Якщо фото не завантажилось, чек усе одно створено, а на його сторінці є «Спробувати ще раз».

**Борги та історія**
- Вкладка **«Борги»**: «Вам винні» / «Ви винні» з розбивкою по людях і групах, кнопки «Повернути» та «Отримано». Короткий підсумок є й на головній.
- Вкладка **«Історія»**: повернення боргів і витрати в усіх групах, фільтри за типом, групою та «лише за моєю участю».

**Інше**
11. Кнопка **Excel** у шапці групи → таблиця з аркушами «Операції» (частка кожного учасника + формула суми витрат), «Баланси», «Хто кому винен».
12. Торкнутися будь-якої операції → «Видалити запис» (лише автор або платник). Якщо видалити витрату з чека, чек знову відкриється для виправлення.
13. Увійти як **Вікторія** й відкрити http://localhost:8000/docs → `GET /api/groups/1/balances` з її токеном → **403 «Немає доступу до групи»**.
14. DevTools → режим телефона: інтерфейс адаптивний (нижня навігація, шторки знизу, камера для фото чека).

## Виправлені помилки (звіт «Помилки в коді»)

| ID | Що зроблено | Тести |
|---|---|---|
| D01 | У БД: `UNIQUE(receipts.operation_id)`, складений FK `(group_id, operation_id) → operations(group_id, id)` (відкладений, без `SET NULL`), перевірка «open ↔ немає операції, closed ↔ є операція». API спершу відкриває чек, потім видаляє операцію в одній транзакції | `test_code_issues.py::test_d01_*` |
| D02 | Запити на запис починаються з `BEGIN IMMEDIATE` ще до читання, тож дії з чеком виконуються строго по черзі; вичерпане очікування блокування → `503` | паралельні тести `test_d02_*` (без виправлення падають) |
| D03 | Пробіли обрізаються в схемі до перевірки довжини: «   » → `422` (профіль, група, назва чека, позиція) | `test_d03_*` |
| D04 | Ліміт загальної суми чека при створенні (`422`) і повторно перед закриттям (`400`, чек не змінюється) | `test_d04_*` |
| D05 | Клієнт показує успіх створення чека окремо від фото, переходить на сторінку чека й дає повторити лише завантаження | `test_d05_*` + E2E |
| D06 | Фото повністю декодується (Pillow), формат визначається за вмістом; нове фото зберігається під новим ім'ям, старе прибирається лише після підтвердження в БД; `photo_version` для оновлення кешу | `test_d06_*` |
| D07 | Точний мінімум переказів: динамічне програмування по підмножинах (до 16 людей із боргами), інакше план із позначкою «мінімальність не доведено»; API і XLSX використовують ту саму функцію | `test_d07_*`, `test_settle_*` |
| D08 | `KASA_ENV=prod` вимагає власний `KASA_JWT_SECRET` (≥ 32 символи), інакше сервер не стартує; секрет не потрапляє в повідомлення | `test_d08_*` |

Зміна обмежень БД не мігрується автоматично: стара база розпізнається за версією схеми (`PRAGMA user_version`) і створюється заново командою `.\dev.ps1 -Reset`.

**Продакшен:** `KASA_ENV=prod`, `KASA_JWT_SECRET=<довгий випадковий рядок>` у змінних середовища.

Розпізнавання тексту чека (OCR) не входить: позиції вводяться вручну, фото зберігається як підтвердження.
Також не входять: доходи, бюджети, статистика, realtime-синхронізація (зараз — автооновлення кожні 3–4 с), деплой.
